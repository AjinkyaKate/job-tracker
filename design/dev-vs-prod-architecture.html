2. Sign-in Flow

"Sign in with Google" — step by step

A sequence diagram. Three actors. Arrows show messages going back and forth in time (top = first, bottom = last).

← Browser sends code to your app

access_token, refresh_token, expiry

INSERT INTO oauth_tokens (user_id, ...)

Why so many steps? Security. The user never types their Google password into your app. Your app never sees the password. Google handles authentication, your app just gets a token to act on behalf of the user.

4. Multi-User Isolation

One database. Three users. Three views.

Alice, Bob, and you all share the same Postgres. The user_id filter is what keeps your data invisible to Alice and Alice's invisible to you.

jobs table (everyone's rows in one place)
id user_id title company status who
142AI PMFoosaved← Alice
242Senior PMBarapplied← Alice
399APMBazsaved← Bob
499FDEQuxsaved← Bob
5108Technical PMWexapplied← You
Alice's request
SELECT * FROM jobs WHERE user_id = 42
→ Sees rows 1, 2
Bob's request
SELECT * FROM jobs WHERE user_id = 99
→ Sees rows 3, 4
Your request
SELECT * FROM jobs WHERE user_id = 108
→ Sees row 5

The bug to NEVER make: Forgetting the WHERE user_id = ? clause in any query. If you ship code that says SELECT * FROM jobs without the filter, Alice sees Bob's data. This is the #1 multi-tenant security failure. Always filter by user_id, every query, no exceptions.

5. Request Lifecycle

When a user clicks "Sync Gmail" — what happens

Tracing one click through every layer. ~5 seconds end-to-end on a warm server.

1
Browser
User clicks the "Sync Gmail" button → JavaScript sends POST /gmail/sync with session cookie.
↓
2
FastAPI receives request
Looks up session cookie → finds user_id. Loads OAuth tokens for this user from DB.
SELECT * FROM oauth_tokens WHERE user_id = 108
↓
3
Call Gmail API
FastAPI uses the access_token to call Gmail. Searches the user's mailbox for LinkedIn alerts since last sync.
GET https://gmail.googleapis.com/gmail/v1/users/me/messages
Authorization: Bearer ya29.a0AfH6...
↓
4
Gmail returns email IDs
FastAPI fetches each email's body. Parses out job alerts.
↓
5
Insert new leads into DB
For each new job alert: insert a row into jobs. Crucially: with user_id = 108.
INSERT INTO jobs (user_id, title, company, status, ...) VALUES (108, 'AI PM @ Foo', 'Foo Corp', 'lead', ...)
↓
6
Return JSON summary
FastAPI sends response back.
{"ok": true, "fetched": 47, "leads": 3, "events": 12, "duration_s": 4.2}
↓
7
Browser updates UI
Toast pops up: "✓ Sync complete · 3 new leads · 4.2s". Card on screen updates with new numbers.

7. What's Actually Different

Dev vs prod: same code, different env vars

The code in both environments is identical. The only differences live in environment variables.

.env (DEV)
ADMIN_USERNAME=admin
ADMIN_PASSWORD=dev-password-123
DATABASE_URL=postgresql://.../dev_db
GOOGLE_CLIENT_ID=DEV_CLIENT_ID...
GOOGLE_CLIENT_SECRET=DEV_SECRET...
GOOGLE_REDIRECT_URI=job-tracker-dev.onrender.com/auth/callback
GEMINI_API_KEY=dev_key_with_lower_quota
.env (PROD)
ADMIN_USERNAME=(none, replaced by Google login)
ADMIN_PASSWORD=(none)
DATABASE_URL=postgresql://.../prod_db
GOOGLE_CLIENT_ID=PROD_CLIENT_ID...
GOOGLE_CLIENT_SECRET=PROD_SECRET...
GOOGLE_REDIRECT_URI=jobtracker.io/auth/callback
GEMINI_API_KEY=prod_key_paid_tier

Critical: The Google OAuth client must be created TWICE in Google Cloud Console — once for dev, once for prod — with different redirect URIs. Otherwise Google rejects the callback.
