Dev vs Production

Two environments for one app, and how to ship safely between them without breaking things for customers.

1. The Idea

What's an environment?

Think of it like running a small business. You have two places where work happens:

🛠️

Your Workshop

Messy. Half-built things. Tools scattered. You try new ideas, break stuff, fix it, try again.

→ Customers never see this.

🏪

Your Storefront

Clean. Polished. Everything works. Customers walk in, find what they need, leave happy.

→ If this breaks, customers leave and don't come back.

In software, the workshop is your dev environment and the storefront is your production environment. Same app, two copies. Different audiences. Different rules.

2. The Problem

Where we are today (risky)

Right now, your job-tracker has only ONE environment. Every change you push goes straight to the live URL. The same place where you experiment is where real usage happens.

Where we want to be (safe)

Two separate environments. Same code, different deploys. Code lives in dev first. Only when you're sure does it move to prod.

DEV (workshop)
job-tracker-dev.onrender.com
  • ✓ Auto-deploys every git push
  • ✓ Test data, fake users
  • ✓ You break it freely
Customers: 0 (just you)
PROD (storefront)
jobtracker.io (or similar)
  • ✓ Manual promote only (you approve)
  • ✓ Real user data
  • ✓ Backups, monitoring, alerts
Customers: real people relying on it
↓
code flows this way, never backwards
3. The Pipeline

How code travels from your laptop to customers

Each step is a check. Each check catches a different kind of mistake. The more checks before prod, the safer.

1
You write code on your laptop
Save the file. Run it locally with uvicorn webapp:app --reload to see if it works at all.
↓
2
git commit + git push
Your code is now in GitHub. Anyone with repo access can see it.
↓
3
Render auto-deploys to DEV
Render detects the push, rebuilds your app, deploys to job-tracker-dev.onrender.com. Takes ~2 minutes.
↓
4
You test the dev URL
Open dev URL, click around, sign in with a test Gmail, sync emails, generate a resume. Make sure nothing's broken.
↓
5
You manually trigger PROD deploy
If dev is good, click "Promote to production" in Render UI. Same code, different environment vars.
↓
6
Customers see the new version
Real users on jobtracker.io now have the new feature. Hopefully smoothly.

The Sign-in-with-Google flow

1
User opens jobtracker.io, clicks "Sign in with Google"
Just a button. Triggers a redirect.
2
Browser goes to Google's "Allow access?" page
Google asks: "Job Tracker wants to read your Gmail to find LinkedIn alerts. OK?"
3
User clicks "Allow"
Google sends them back to your app with a temporary code.
4
Your app trades the code for an access token + refresh token
Stores both in DB, linked to a user_id. Now your app can read this user's Gmail whenever it wants.
5
App sets a session cookie for that user
From now on, every request from this user is recognized. They see only THEIR jobs, leads, and resumes.

Side note: You already use OAuth in the Gmail sync feature (where the app reads your Gmail). The "Sign in with Google" flow is the SAME OAuth pattern, just used for login instead of email reading. Same plumbing, different purpose.

5. When it breaks

"Works on dev but broken in prod" — why?

This is the most frustrating bug to have. You shipped the same code. Why does it act differently? Usually one of these four reasons.

🔑

Different env vars

Dev uses your test Gemini key. Prod uses a different key with rate limits. Same code, different keys, different behavior.

Fix: keep an .env.dev and .env.prod, compare them.
📊

Different database state

Dev has 5 test users. Prod has 5,000 real users. Code that ran in 0.1s on 5 rows times out on 5,000.

Fix: load production-like data into dev. Test at scale.
🔄

Missing migration

You added a new column locally. Dev ran the migration. You forgot to run it on prod. Code references a column that doesn't exist there.

Fix: migrations auto-run on every deploy (tracker.init_db handles this).
🌐

External service config differs

Dev's Google OAuth has callback URL = localhost. Prod needs jobtracker.io. If you forgot to register the prod URL with Google, OAuth fails.

Fix: register BOTH callback URLs in Google Cloud Console.

The Golden Rule

Keep dev and prod as identical as possible. Same Python version, same database engine, same env var names. The only things that should differ are the SECRETS (different keys) and the DATA (test vs real).

6. Action Plan

What we'll actually do, step by step

A
Stabilize dev first
Fix the Gmail autosync failure (we left that open). Make sure dev is rock-solid before promoting anything to prod.
B
Spin up a second Render web service for PROD

C
Spin up a second Postgres for PROD
Separate database means dev test data never mixes with real prod data.
D
Configure Render to auto-deploy dev, manual prod
Render Settings: dev = "Auto-deploy on push", prod = "Manual deploy" (you click a button when ready).
E
Add Sign-in-with-Google to the app
Replace HTTP Basic Auth with OAuth login. Add a users table. Tag every job/lead/resume with user_id.
F
Test multi-user on DEV with 2-3 different Gmail accounts
Make sure user A doesn't see user B's data. This is the make-or-break test.
G
Promote to PROD
Manual deploy. Watch logs. If anything looks wrong, instant rollback. First customer can now sign up.

Each step is small. Each one teaches you a different piece. By step G, you'll have shipped a multi-tenant SaaS with a proper deploy pipeline. Resume material on its own.
