DevOps · Production-Grade Systems

From code to customer

How a real engineering team takes one person's code and turns it into a service running 24/7 for millions of users. Tools, roles, pipelines, and the rituals around them.

1. The Definition

What does "production grade" actually mean?

It's not about the code being clever. It's about the system surviving real-world chaos: traffic spikes, bad inputs, network hiccups, hardware failures, bugs you didn't catch. A production-grade system makes promises and keeps them.

⏱️

Uptime

Service is reachable when customers need it. "99.9%" = ~8 hours of allowed downtime per year. "99.99%" = ~52 minutes.

🛡️

Reliability

Same input = same output. No flaky behavior. Errors are caught, logged, and handled gracefully.

📈

Scalability

Works with 10 users AND 10 million. Performance doesn't fall off a cliff.

🔍

Observability

When something breaks, you can SEE why. Logs, metrics, traces, dashboards.

🔄

Recoverability

When something breaks, you can roll back fast. Backups, rollback plans, hot fixes.

🔐

Security

Customer data protected. Auth gates in place. Secrets in vaults, not code. Audit trails for changes.

Your code only contributes to ~30% of "production grade." The other 70% is the system, the team, the rituals, and the tooling around the code. That's what DevOps is about.

2. Who Does What

The team behind a production system

In a mature engineering org, no single person ships code to production alone. Different roles have different gates and different expertise. Your company's flow (dev writes → lead approves → DB team raises ticket → QA tests → release) is normal.

👨‍💻
WRITES CODE
Software Engineer (Dev)
Writes features, fixes bugs, opens pull requests.
Tools: VS Code, Git, GitHub, language stack
🧐
REVIEWS
Tech Lead / Senior Engineer
Reviews PRs. Catches design issues, security issues, performance concerns. Approves merge.
Tools: GitHub PR reviews, design docs
🚀
SHIPS
DevOps / Platform Engineer
Builds and maintains the deployment pipeline. CI/CD, infrastructure, secrets management.
Tools: Jenkins, GitHub Actions, ArgoCD, Terraform, Kubernetes
🚨
WATCHES
SRE (Site Reliability Engineer)
Monitors prod. On-call rotation. Defines SLOs. Investigates incidents.
Tools: DataDog, Grafana, PagerDuty, Sentry
🗄️
OWNS DATA
DBA / Data Engineer
Approves schema changes. Runs migrations. Backups, replication, performance.
Tools: PostgreSQL, MySQL, migration tools (Flyway, Alembic)
🧪
VALIDATES
QA Engineer / SDET
Writes test suites. Runs regressions. Signs off before prod release.
Tools: Cypress, Playwright, Postman, JMeter

Note: In small startups, ONE person plays multiple roles (you've been all 6 on your job-tracker). In a 500-person eng org, each role has dedicated people. The roles don't go away, they just get specialized.

3. The CI/CD Pipeline

From your laptop to production, step by step

CI = Continuous Integration. CD = Continuous Deployment (or Delivery). Together they form the automated path from "code written" to "code live."

1
Engineer commits code
git push origin feature/my-thing
↓
2
CI server kicks in (automated)
GitHub Actions / Jenkins detects the push. Spins up a fresh environment.
Run linter → Run unit tests → Run integration tests → Build artifact
↓
3
All green? → Open Pull Request
If any test fails, the engineer fixes before going further. PR is opened automatically when ready.
↓
4
Tech Lead reviews the PR
Reads the diff. Asks questions. Suggests changes. Approves OR rejects.
↓
5
Merged to main branch → auto-deploys to DEV
Merge triggers another pipeline. Code is built into a Docker image, pushed to a registry, then deployed to dev/staging.
↓
6
QA tests on staging
Manual + automated test runs against staging. Edge cases, regressions, mobile, multi-region.
↓
7
QA approves → promote to PROD (manual gate)
A human clicks "Promote." OR if you trust your tests fully, this can be automatic (true Continuous Deployment).
↓
8
Deployed to PROD with monitoring
SRE/DevOps watches dashboards for the first 30-60 min. Error rates, latency, traffic. Rollback ready.

Common tools at each stage: Git/GitHub (source) → GitHub Actions / Jenkins / GitLab CI (CI runner) → Docker (containerize) → AWS ECR / Docker Hub (registry) → Kubernetes / ECS / Render (deploy target) → DataDog / Sentry / Grafana (observability). Each company picks 1-2 from each category.

4. Environments

More than just dev and prod

Real systems have 3-5 environments, not just 2. Each one catches different bugs.

DEV
Developer's local machine OR shared dev server
Run by: each engineer. Test data. Breaks freely.
↓
STAGING
Mirror of prod, but with test data
QA tests here. Matches prod infra exactly. Catches "works locally, breaks in prod-like infra" bugs.
↓
UAT
User Acceptance Testing
Product/business team tries the feature. Sometimes real customers in a beta program.
↓
CANARY
Tiny slice of real users (1-5%)
Real prod, but only some users see the new version. Watch error rates. If anything breaks, only a small group affected.
↓
PROD
All real users
100% of traffic. Where it really has to work.
5. The Database Track

Why DB changes are a separate, scarier flow

Code can be rolled back in 1 minute. A botched database migration can take HOURS to recover from, sometimes requires restoring from backup, and can corrupt customer data. That's why DBAs have a separate gate.

Typical DB change flow

1. Dev raises a ticket for the schema change
"I need a new column X on table Y for feature Z."
↓
2. DBA reviews
Checks performance impact, indexing, naming conventions, lock implications. Approves or asks for changes.
↓
3. Migration script written + tested on staging
Tools like Flyway, Liquibase, Alembic, Django migrations. Idempotent (safe to re-run).
↓
4. Backup prod DB
Before touching anything in production. Always always.
↓
5. Run migration during a maintenance window
Off-peak hours. Maybe a 5-min downtime announced ahead.
↓
6. Verify + deploy the code that uses the new schema
Migration runs FIRST, code runs SECOND. Never the other way around.

Golden rule: Schema changes always go LIVE BEFORE the code that depends on them. If you deploy code first and migration fails, your app crashes in prod.

6. Region-Based Rollouts

Why you saw "feature deployed to RU and DC, others later"

Big companies don't ship to the whole world at once. They roll out region by region, watching for issues. Your company's "RU and DC" pattern is exactly this.

Day 1: feature launches in ONE region
REGION A (DC)
v2.5 (new) ✓
Watch error rates for 24h
REGION B (RU)
v2.4 (old)
REGION C (EU/US)
v2.4 (old)
↓ 24h later, no issues seen ↓
Day 2: expand to a second region
REGION A (DC)
v2.5 ✓
REGION B (RU)
v2.5 ✓
REGION C (EU/US)
v2.4
↓ another 24h, still clean ↓
Day 3: full rollout
REGION A
v2.5 ✓
REGION B
v2.5 ✓
REGION C
v2.5 ✓
Why this works:
  • • Bad bugs surface in 1 region first, not globally
  • • Rollback impacts 33% of users, not 100%
  • • You can compare metrics (v2.5 region vs v2.4 region)
  • • Confidence builds before the full launch
Trade-offs:
  • • Slower full rollout (3-7 days vs minutes)
  • • Code must support multiple versions running simultaneously
  • • DB changes need to work for BOTH v2.4 AND v2.5 code
  • • More infrastructure cost
7. Feature Flags

Ship code without launching it

A feature flag is an if-statement in code that the team can flip ON/OFF without redeploying. Used everywhere in modern systems.

if feature_flag("new_checkout_flow", user_id):
    return render_new_checkout()    # ← new code, only some users see this
else:
    return render_old_checkout()    # ← safe fallback
🧪
A/B test
50% see new feature, 50% see old. Measure which performs better.
🎯
Targeted launch
Enable for specific customer accounts first (beta). Roll out to all later.
🚨
Instant kill switch
Production bug? Flip flag to off. Code is still deployed but inactive. No redeploy needed.
Common tools: LaunchDarkly, GrowthBook, Unleash, ConfigCat, or DIY with a config table.
8. Observability

How you see what's happening inside the system

When something breaks at 3am, you need to know WHY without SSH-ing into a server. Observability is the eyes and ears of your production system.

📝
Logs
Text records of what happened. "User 42 clicked button. Server processed in 230ms. Returned 200."
Tools: ELK, Datadog Logs, CloudWatch, Loki
📊
Metrics
Numbers over time. Request count, error rate, response time, CPU usage, memory.
Tools: Prometheus, Grafana, Datadog, New Relic
🔬
Traces
Follow one request through ALL the services it touched. "Request X spent 50ms in auth, 200ms in DB, 30ms in API call."
Tools: Jaeger, OpenTelemetry, Datadog APM
🔔 Alerting
When metrics cross a threshold (error rate > 1%, response time > 2s), the system pages someone via PagerDuty / Opsgenie / Slack. On-call engineer wakes up.
📋 Dashboards
Curated views of metrics. "Service health overview", "Database performance", "User signups". Looked at every morning during standup.
9. Incident Response

When prod breaks at 3am

Every team has incidents. The mature ones have a playbook. Here's roughly what happens.

1
Detection
Monitoring alerts fire. Customer support sees angry tickets. Status page updated to "Investigating."
2
Triage
On-call engineer wakes up, checks dashboards. What's broken? How bad? Who's affected? Incident commander assigned.
3
Mitigate
Stop the bleeding first. Roll back the bad deploy. Flip the feature flag off. Scale up servers. The fix can come later.
4
Resolve
Once stable, find the actual root cause. Write a real fix. Deploy it. Status page updated to "Resolved."
5
Postmortem (blameless)
24-48 hours later, the team writes a doc: what happened, what failed, what we'll change. NOT "whose fault." Focus on the system, not the person.
